# 分层分片数据并行（HSDP）的设计原理

> 本文讲一类「自己管理参数布局、按层级组织 ZeRO」的数据并行设计，以及它相对 PyTorch FSDP2 省掉了哪些开销、付出了哪些代价。内容是通用的工程原理，不对应某个具体产品的实现。

## 0. 出发点：FSDP2 的几项固定开销

FSDP2（`fully_shard`）用 `DTensor` 表示分片参数，在 forward / backward 的 hook 里完成「收集权重」和「归约梯度」。它的通用性很好，但有几项开销是结构性的：

1. **梯度归约前的拷贝**。反向结束后，要把每个参数的梯度拼进一块连续的通信 buffer（必要时顺便转成 fp32 的规约精度），再做 ReduceScatter。PyTorch 的实现里这是一个 `chunk_cat` 类的 kernel。
2. **权重收集后的拷贝**。AllGather 得到的是一块连续 buffer，还要再切回每个参数各自的存储（`split_with_sizes_copy` 类的 kernel）。
3. **梯度累加的显存/通信二选一**。做梯度累加（GA）时，要么每个 micro-batch 都 ReduceScatter（通信多），要么关掉同步、把完整的 fp32 梯度一直留到最后一个 micro-batch（显存多）。

前两项是纯访存的拷贝，耗时随参数量线性增长，和计算量无关。每卡计算越少（batch 小、或长序列被切到很多卡上），它们在一步里占的比例越高。

下面介绍的设计，核心就是**让参数在整个训练过程中一直以「扁平 buffer」的形式存在**，从而让通信直接作用在模型真正使用的存储上，省掉这两次拷贝。

## 1. 分层分片：一个参数，三种切法

设数据并行共有 `P` 个 rank。定义三个嵌套的分片规模，要求逐级整除：

```
P  % Z1 == 0      # Z1：优化器状态的分片数（P / Z1 份副本）
Z1 % Z2 == 0      # Z2：梯度的分片数
Z2 % Z3 == 0      # Z3：参数的分片数
```

于是每个参数同时有四个「视图」：完整（full）、按 Z3 切、按 Z2 切、按 Z1 切。对应 ZeRO 的三个阶段：

| 视图 | 存什么 | 何时存在 |
|---|---|---|
| full | 前向/反向用的完整权重、反向产生的完整梯度 | 只在用到的那一层、那一小段时间 |
| zero3 分片 | 平时持有的运行权重 | 常驻 |
| zero2 分片 | 跨 micro-batch 累加的梯度 | GA 期间常驻 |
| zero1 分片 | fp32 主权重、优化器状态、最终梯度 | 常驻 |

三档可以独立取值。例如取 `Z3 = 节点内卡数`、`Z1 = 全部卡数`：权重只在节点内收集（走 NVLink，快），优化器状态切得最碎（省显存）。这就是「混合」的含义——**副本维度和分片维度不必一刀切**，同一个参数的不同状态可以按不同粒度分布。

## 2. 核心抽象：存储、视图、打包

实现这套分层分片只需要三个概念：

- **存储节点**：一块只按字节计量的显存，带「分配 / 释放」回调。它是真正的内存所有者。
- **静态张量**：在存储节点上加 shape 和 dtype，并用一条链把 `full → zero3 → zero2 → zero1` 串起来，每一级记录「怎么从上一级切出来」。
- **张量列表**：同 dtype 的一批静态张量拼成一个扁平 buffer，附带偏移表。

张量列表是省掉拷贝的关键：**一整层的几百个参数在内存里本来就是连续的一块**。AllGather 直接写进这块连续 buffer，各参数是它上面的视图，不需要再切；ReduceScatter 直接读梯度所在的连续 buffer，不需要再拼。

### 按需分配、用完就还

参数对象创建时，底层存储是**空的**。只有到收集权重时，分配回调才把真实数据挂上去；用完调用 `storage.resize_(0)` 还给分配器。

这带来两条贯穿全文的约束：

1. **运行期权重的地址不稳定**。任何代码如果在释放点之后继续持有权重视图，就是 use-after-free。所以自定义算子在 backward 里要保存**参数对象本身**（由它在需要时重新提供数据），而不是 forward 时拿到的权重视图。
2. **显存峰值由调度决定**，而不是由静态大小决定。什么时候分配、什么时候释放，直接决定峰值。

## 3. 初始化：先定布局，再分配

```
1. 参数转换      每个 nn.Parameter 换成框架自己的参数对象：
                 前向权重(bf16) / 主权重(fp32) / 梯度(fp32) / 优化器状态
2. 划定分组      标出哪些模块（通常是每个 Transformer 层）作为一次收集的单位
3. 生成分片计划  决定打包方式、对齐、每级尺寸、每个 rank 持有哪段
4. 生成调度器    运行期的「收集/归约」调度器、优化器调度器
5. 初始化        到这一步才真正创建通信组、分配常驻存储、编译优化器批次
```

前四步都只写元数据。通信组也可以「延迟创建」：先用一串切分动作描述「我属于哪个子组」，到第 5 步再统一建。这样在不分配任何资源的情况下就能先把拓扑和布局算清楚，算错了直接报错，不会出现「组建好了才发现拓扑不对」。

代价是**布局在第 3 步就定死了**：运行期不能增删参数、不能改形状。作为交换，通信计划（哪些张量合并成一次 collective）也能全部预先算好。

## 4. 训练一步的调度

### 4.1 主流程

```
清零梯度
for 每个 micro-batch:
    进入 micro-batch 上下文（标记是否首个 / 末个）
      每层 forward 前：收集本层权重，并预取下一层
      forward
      每层 backward 前：如有需要再收集反向用的权重；申请本层 full 梯度 buffer
      每层 backward 后：不立刻通信，把「清理动作 + 它依赖的 CUDA event」入队
归一化梯度（除以样本数）
求梯度范数（各 rank 部分和 → all_reduce）
梯度裁剪 → 优化器更新 → 主权重写回运行权重
```

### 4.2 权重：带「待清理」状态的状态机

前向和反向需要的权重格式可能相同，也可能不同（比如反向只要转置后的低精度副本）。用一个显式状态机描述一层权重的生命周期：

```
空 ──收集──→ 前向持有 ──用完──→ 前向待清理 ──执行清理──→ 空
                 │                    │
                 │（前后向同格式）     └─（反向要另一份）→ 前向待清理 + 反向持有
                 └──────────────→ 反向持有 ──用完──→ 反向待清理 ──→ 空
```

关键是**「待清理」不等于「已释放」**。用完时只把状态标成待清理，真正的释放动作连同它依赖的 CUDA event 一起排进通信 stream。这样：

- 如果紧接着又要用同一份权重（比如前后向格式相同），直接从「待清理」退回「持有」，免去一次重新收集。
- 收集、释放都按入队顺序在通信 stream 上执行，天然形成流水线。

### 4.3 梯度：两段归约

反向结束时也不立刻归约，而是入队两段动作：

```
第一段（每个 micro-batch 都做）：
    full 梯度 ──ReduceScatter，累加模式──→ zero2 分片；随后释放 full buffer
第二段（只在最后一个 micro-batch 做）：
    zero2 分片 ──ReduceScatter，覆写模式──→ zero1 分片（真正执行优化器的 rank）
    若 zero1 之外还有副本维度，再对副本做一次 all_reduce
```

和 FSDP2 对比：

- 第一段等价于 FSDP2「每个 micro-batch 都同步」的做法，full 梯度只活一个反向区间，显存按分片算。
- 第二段把「最终归约到更新者」推迟到最后，且规模是分片后的。当 `Z2 > Z1`（梯度切得比优化器状态还碎）时，跨副本的那部分通信只在每步末尾做一次，而不是每个 micro-batch 一次。

也就是说，第 0 节里的第 3 项矛盾被拆成了两级：**节点内（或较小的组内）每个 micro-batch 同步一次，跨副本每步只同步一次**。

### 4.4 一条通信 stream 就够

权重收集和梯度归约可以**共用同一条通信 stream**。入队顺序本身就是流水线：当前层的权重收集 → 上一层排队的梯度清理 → 下一层的权重收集。拆成两条 stream 反而要多插事件同步，而对同一个 communicator 的操作本来就串行执行。用 Nsight Systems 看这类实现，所有 NCCL kernel 会落在同一条 stream 上；FSDP2 通常把 AllGather 和 ReduceScatter 分在两条。

## 5. 通信层

### 5.1 普通路径：合并调用

在第 3 步生成调度器时，就把同一个通信组、同一 dtype、各 rank 分片等长的张量**合并成一个计划**，执行时用一次 `ncclGroupStart/End` 批量下发。只有分片不等长的才单独调用。

ReduceScatter 还有一个小优化：分片等长时，本 rank 的输出可以和输入里对应那一段**共享存储**，省一次拷贝。

### 5.2 对称内存路径

更进一步，可以不用 NCCL 内置的 AllGather / ReduceScatter，而是基于 NCCL symmetric memory（以及 host 发起的远端写）自己组装：

- **AllGather**：先跨节点把本 rank 的分片直接写进对端预先注册的窗口，并发信号；对端等信号到齐后，再在节点内用 copy engine 把数据分发给本机其他 rank。
- **ReduceScatter**：先在节点内把各卡的梯度规约成部分和（用 fp32 暂存），再跨节点做 all-to-all，把每个 rank 负责的分片凑齐。

好处是少一次「先拷到输出 buffer 再收集」的中转，而且可以把通信从计算 SM 上挪开。代价是约束很硬：

- AllGather 通常要求**各 rank 分片等长**，因为远端写需要一致的偏移。
- 分层 ReduceScatter 用 fp32 暂存部分和时，往往只支持 fp32 输入和累加模式。

遇到不满足的配置，应该**明确报错**而不是悄悄退回慢路径，否则用户会在不知情的情况下跑在错误的实现上。

### 5.3 窗口注册与显存统计陷阱

对称内存要求通信用的显存是预先注册过的窗口。所以动态 buffer 不能走 PyTorch 的缓存分配器，而是一次性用 `ncclMemAlloc` 申请一大块，再按生命周期把各个逻辑 buffer 映射进去（生命周期不重叠的可以复用同一段）。

> **陷阱**：这类显存**不计入** `torch.cuda.max_memory_allocated / max_memory_reserved`。结果是开了对称内存的配置，框架日志里的显存峰值可能只有普通配置的一半左右，而用 `nvidia-smi` 采样，它的实际占用反而是几种配置里最高的——通信 buffer 全被挪到了统计之外。
>
> 只要方案里出现 `ncclMemAlloc`、NVSHMEM 或其他自己管理显存的机制，比较显存就必须用 `nvidia-smi` 或 `cudaMemGetInfo`。

## 6. 优化器与梯度写入

### 6.1 优化器按「更新单位」分工

优化器状态按元素切分，但不同优化器对「能否只拿一部分元素就算」的要求不同。可以给每种优化器定义一个**更新单位**：

- Adam 是逐元素的，单位是 1 个元素，任何分片都能独立完成。
- Muon 这类需要对整个矩阵做正交化的，单位是整个参数。

如果一个单位跨了多个 rank 的分片，就选**持有该参数最多元素的 rank** 来执行，其余 rank 用点对点通信把数据送过去、算完再送回来。

参数切得越碎，跨 rank 的单位越多，点对点通信越多。所以分片计划通常按「整层打成一个扁平桶」来切，而不是每个参数单独切。

### 6.2 梯度直写（gradient accumulation fusion）

普通路径下，autograd 先产出 `param.grad`（低精度），再由 hook 加进 fp32 梯度 buffer。这多了一个临时张量和一次逐元素加法。

**直写路径**：自定义 `autograd.Function` 的 backward 直接把权重梯度写进 fp32 梯度 buffer，并对权重返回 `None`，让 autograd 完全不碰 `.grad`：

```python
# 概念示意
target = parameter.main_grad                     # fp32 梯度 buffer
beta = 0 if first_write_this_round(parameter) else 1
torch.addmm(target, dy.T, x, beta=beta, out_dtype=torch.float32, out=target)
return grad_x, None, None
```

`out_dtype=fp32` 让 GEMM 的 fp32 累加器直接落到 buffer 里，中间不经过 bf16 舍入，既省带宽又更准。这个思路和 Megatron-LM 的 gradient accumulation fusion、以及 torchtitan PR #5250 的原地 wgrad 累加是一致的；区别主要在于「累加进哪个 buffer、怎么判断是第一次写」。

**怎么判断是第一次写**：不能用 `param.grad is None`，因为这条路径根本不碰 `.grad`。需要一个显式的「本轮已写过」集合，挂在梯度 buffer 的分配回调上，**buffer 每分配一次就清空一次**：

- 同一个 micro-batch 里参数被用了多次：第一次 `beta=0` 覆写，之后 `beta=1` 累加。
- 走普通路径的参数不参与这个机制，一律累加。

**两个必须注意的坑**：

1. **保存参数对象，不要保存权重视图**。理由同第 2 节：运行期权重可能已被释放；激活重算（activation checkpointing）的 saved-tensor hook 也可能把张量子类拆开。
2. **直写的 buffer 一般不预先清零**，正确性完全依赖「第一次写」覆盖每一个元素。如果底层是**分组 GEMM**（例如 MoE 按专家分组计算权重梯度），某些实现在「直接写输出、不读累加输入」的模式下会**跳过没有数据的分组**——也就是没有 token 被路由到的专家。这些专家的梯度就是 buffer 里上一次残留的脏数据。表现非常隐蔽：不会崩，只会**偶发地、每次运行都不一样地**让梯度范数变大，因为残留内容取决于显存复用的历史。修法是让 kernel 对空分组也写零，或者在覆写前先清零。

### 6.3 融合优化器 kernel 的一个性能坑

Adam + EMA 写成一个融合 kernel 时，每一步需要三个**只依赖 step、不依赖元素**的系数：`1 - β1^t`、`1 - β2^t`，以及 EMA 衰减系数（形如 `1 - (1+t)^(-power)`）。Apex 的做法是在 host 侧每组参数算一次，作为标量传进 kernel。

如果为了避免 host 往返，把它们挪到 device 上算，但放在**每个 warp 里各算一遍**，就会出问题：`pow` 是超越函数，而为了和 host 侧数值对齐，EMA 那项往往用 FP64 算。一些为 AI 精简了 FP64 单元的 GPU 上，FP64 吞吐比 FP32 低得多。于是本该受显存带宽限制的逐元素 kernel，变成被重复的 FP64 计算卡住，可以慢出一个数量级以上。

修法：**先用一个小 kernel 给每个参数只算一次这三个系数，写进一张小表；主 kernel 只读这张表**。公式和数据类型都不变，结果逐位一致。只把 FP64 换成 FP32 并不够：重复计算还在，而且结果不再和参考实现逐位一致。

一般化的教训：**只依赖 step、不依赖元素的量，不要放进逐元素 kernel 的热路径里重复算。**

## 7. 与 FSDP2 对照

| 维度 | FSDP2 | 分层分片设计 |
|---|---|---|
| 参数表示 | 每参数一个 `DTensor` | 整层扁平 buffer + 四级视图链 |
| 权重收集后 | 切回各参数的存储（拷贝） | 各参数直接是 buffer 上的视图 |
| 梯度归约前 | 拼进通信 buffer（拷贝，常带转换） | 梯度本来就在连续 buffer 里 |
| 分片粒度 | 参数、梯度、优化器状态同一套分片 | 三者可以按不同组大小分片 |
| GA 期间 | 每 micro-batch 同步，或关同步留完整梯度 | 组内每 micro-batch 同步，跨副本每步一次 |
| 权重释放 | `reshard_after_forward` 策略 | 带「待清理」状态的状态机，可复用 |
| 优化器 | 各 rank 处理自己的分片 | 按更新单位分配执行者，必要时点对点搬运 |
| 通信 | NCCL collective | collective，或对称内存 + 远端写 |

## 8. 代价

1. **布局静态**：运行期不能增删参数、改形状；换模型结构就要重新生成计划。
2. **权重地址不稳定**：所有持有权重视图的地方都要小心生命周期，这是最容易出隐蔽 bug 的地方。
3. **约束多、校验多**：等长分片、整除关系、dtype 组合……配置不对时应该直接报错，代价是报错多、上手门槛高。
4. **对称内存路径的限制更硬**，而且显存统计口径会骗人（见 5.3）。
5. **优化器的点对点通信和分片粒度耦合**：参数越碎越贵；整层打包能缓解，但会让单次收集的峰值更集中。
6. **和编译栈不兼容**：直写梯度依赖「读 / 改运行期状态」，`torch.compile` 这类 trace 方式难以表达，通常需要显式关闭。
